# Cybele AI Design Assistant — Progress Report

**Last updated:** 2026-06-10
**Project:** AI-assisted branded document and design generation for Cybele Software

---

## Project Vision

Build an AI-powered system that enables the Cybele design team to:

1. **Brand documents** — Take unbranded content and produce branded PDFs/PPTX
2. **Generate illustrations** — Create article illustrations following brand guidelines, export to Figma as SVG
3. **Generate blog covers** — Produce on-brand hero images for blog articles following a reverse-engineered visual system
4. **Generate architecture diagrams** — Produce Thinfinity product architecture diagrams as native Figma-compatible SVG in the official Cybele "pill" visual system
5. **Co-design in Figma** — Push and iterate designs directly in Figma via MCP integration
6. **Web App for the team** — A shared interface so all team members can leverage these capabilities

## PPTX Generation Pipeline

> **Two paradigms of this pipeline coexist by design**, chosen by **source-document format**:
>
> - **Source is a text format** (DOCX / TXT / MD / Google Docs / etc.) → use the **from-scratch generator** (`python-pptx`, one builder function per slide).
> - **Source is a rendered artifact** (PDF / PPTX / image) → use the **brand-a-source pipeline** (ingest the source PPTX or convert PDF/image to a content PPTX, then apply branding).
>
> Slide count is dynamic, dictated by source content. Closing-slide language always matches the source — the from-scratch transplant preserves the closing's visual structure byte-for-byte but translates its text content; the brand-a-source pipeline does the same on its template's closing.

### From-Scratch Editorial Generator — `build_pptx.py`

**Deck:** *VDI & VDA para Universidades* — Cybele commercial proposal, editorial style **(palette 06/26)**, 13.33×7.5" widescreen. Slide count is dynamic per source document. Output for this test case: `VDI_VDA_Universidades_v3.pptx` (10.6 MB, 27 slides for this specific source).

**Paradigm shift vs the older pipeline:** the deck is authored entirely in code (no source PPTX is branded). Every shape, card, and text run is placed by a per-slide builder function. Dimensions stay at **native 13.33×7.5"** (not downscaled to 10×5.625") so the transplanted closing slide drops in without scaling.

**Design tokens** (`build_pptx.py`, "DESIGN TOKENS" block) — the **canonical palette 06/26** (the current Cybele palette going forward; supersedes the older `#0A74D6` / `#0B1A3B` documented above as "Primary Blue / Navy" — those are kept in §"Brand Tokens Extracted" as historical reference only):

| Token | Hex | Role |
|---|---|---|
| `NAVY` | `#0A1A2F` | Dark-mode background |
| `CANVAS` | `#EEF4FB` | Light-mode background (very light blue) |
| `BRAND_BLUE` | `#0F7FE0` | Primary — titles, accents, solid cards |
| `BLUE_LIGHT` | `#5BAFFF` | Accent on navy |
| `MINT` | `#3DCCA1` | Bullet dots, positive accent |
| `ORACLE_RED` | `#C74634` | Negative accent, "VPN tradicional" tag |
| `TEXT_PRIMARY` | `#2E2E2E` | Body text on canvas/white |
| `TEXT_SECONDARY` | `#6B7280` | Descriptions, subtitles |
| `TEXT_ON_NAVY_MUTED` | `#A8B0BC` | Muted text on navy |
| `FOOTER_TEXT` / `DARK_FOOTER_TEXT` | `#CCCCCC` / `#4A6A90` | Low-contrast footer (intentional) |
| `DARK_CARD` | `#122542` | Card fill on dark slides (borderless) |

**Typography:** Inter **Light / Regular / Medium / SemiBold** only. `set_run()` maps `bold=True` + `font="Inter"` to **Inter SemiBold** (no faux-bold, no Thin/ExtraLight).

**Card system (borderless, shadowless, constant-radius):**
- `add_card_white` (light mode), `add_card_dark` (`DARK_CARD` fill, navy slides), `add_card_brand` (solid brand-blue, used for "the solution" on comparison slides).
- **No borders** — cards are distinguished purely by fill contrast (white on canvas, `DARK_CARD` on navy).
- **No shadows** anywhere in `ppt/slides/` (audit = 0 `outerShdw`/`innerShdw`/`reflection`/`softEdge`).
- **Constant absolute corner radius:** `CARD_RADIUS_EMU = 22860` (= 0.025"). `add_rect`'s `radius_emu` parameter recomputes `radius_frac` per shape so the *visual* radius is identical regardless of container size.

**Dark-mode mix (~22%, dispersed):** roughly 1-in-5 slides are dark (navy bg + `DARK_CARD` containers + white/muted text), spread throughout the deck rather than clustered. Concrete distribution depends on the source content.

**Dynamic footer numbering:** `_count_slide_builders()` counts the `build_slide_*` functions in the module and overwrites `TOTAL_SLIDES` at `build()` time. `add_footer(slide)` infers the 1-based index from `prs.slides` and the total from `TOTAL_SLIDES` (pass `dark=True` on navy slides). Cover and closing carry no standard footer (each has its own bottom design). Add or remove a `build_slide_*` and the whole deck re-numbers automatically.

**Closing-slide transplant** (`replace_slide27.py`) — preserves a hand-made closing slide pixel-identically without inheriting the deck's theme:
1. Inserts the source `cierre.pptx` slide **byte-for-byte**.
2. Copies its **entire layout → master → theme chain** (e.g. `slideLayout1 → slideLayout12`, `slideMaster1 → slideMaster2`, `theme1/theme2 → theme2/theme3`), rewriting all internal `_rels` references.
3. Registers the new parts in `[Content_Types].xml`, `presentation.xml.rels`, and `presentation.xml`.
4. Copies the closing's media with a `cierre_` prefix to avoid collisions.
5. Runs **`force_white_hyperlinks()`** — rewrites `<a:hlink>`/`<a:folHlink>` in the transplanted themes to `FFFFFF` (otherwise PowerPoint paints every `<a:hlinkClick>` run in Office-blue `#0563C1`, overriding the hardcoded white).
6. **Language rule:** preserves visual structure byte-for-byte but **translates text content to match the source-document language**.

**Build commands:**
```bash
cd pptx_work
python3 build_pptx.py                 # → output/<deck>_v3.pptx
python3 replace_slide27.py            # transplant cierre → output/<deck>_v3_with_cierre.pptx
# Verify:
cd output && rm -f *.pdf slide-*.jpg
soffice --headless --convert-to pdf <deck>_v3_with_cierre.pptx
pdftoppm -jpeg -r 80 <deck>_v3_with_cierre.pdf slide
```

**Quality gate:** shadow audit = 0 across `ppt/slides/` (themes carry ~20 latent effect refs that don't affect the render); slide size = `12191969 × 6858000` EMU (13.33×7.5"); footer spot-check confirms first and last slides are footer-less and the rest read `NN / TOTAL`.

**Key decisions (rationale):**
- **Theme transplant > link-stripping** for hand-made closing slides — preserves pixel-identical output where stripping `<a:hlinkClick>` runs from a rebuilt slide could not.
- **Constant absolute corner radius** via per-shape `radius_frac` keeps every container visually consistent regardless of size (avoids the "bigger box ⇒ rounder corner" artifact).
- **Contrast-only cards** (no borders, no shadows) carry the editorial look; mode is signaled by `DARK_CARD` vs white fill, not by strokes.

**Assets** (in `assets/`): `lockup_thinfinity_oracle.png`, `cybele_isologo.png` (white, cover), `bg_navy_cover.jpg`, `bg_navy_closing.jpg`, and `cybele_icons/` (63 PNGs = 21 Figma icons × 3 variants, consumed by `add_icon(name, variant=...)`).

### Brand-a-Source Pipeline — `build_ciso_pptx.py` (reference impl)

Used when the source is a rendered artifact (PDF / PPTX / image). The pipeline ingests the source PPTX, swaps the cover/closing for a standard 2-slide template, and applies branding/cleanup passes.

**Standard 2-slide template (`Copy of VDI_VDA_Universidades_Editable.pptx`):**
- Cover: blue wave bg, Thinfinity + Oracle logos, white title + subtitle. Title + subtitle updated per document; tagline blanked.
- Closing: "Thanks for watching!" + contact info + social icons + animated GIF. Hyperlinks stripped from contact runs (XML `<a:hlinkClick>` overrides theme blue otherwise); contact text forced white. "Thanks for watching!" stays blue (`#0A74D6`); copyright stays gray.
- **Always use this template** — never preserve the source file's own cover/closing.
- **Language-coherence rule:** closing text content is translated to match the source-document language (same rule as the from-scratch transplant — see §6 above).

**Pipeline steps:**
1. Open the 2-slide template.
2. Insert N content slides between cover and closing via `python-pptx`.
3. Reorder XML `sldIdLst` so closing is last.
4. Apply branding pass to content slides: layouts (`two_card_slide`, `content_with_items`, `icon_content_slide`, `add_section_divider`), section dividers (navy bg, number, accent line, white title), Inter SemiBold 18pt headers / Inter Regular body, flat fills, logos in footer, single-digit numbered circles (0.35", 12pt).
5. **Nuclear shadow removal** via `_nuke_effects_from_xml()` — cleans shapes, layouts, masters, AND theme XML (the theme's `effectStyleLst` is what makes per-shape cleanup insufficient).
6. Typography enforcement pass: no italics, no Thin/Light/ExtraLight variants; blue text capped at 18pt.
7. Hyperlink color fix on closing: strip all `<a:hlinkClick>` + clean `endParaRPr` colors.

**Dimensions:** output at 10"×5.625" (Google Slides compatible). Source typically at 13.33"×7.5", converted at branding time.

**Helper functions:** `add_header_bar`, `add_section_divider`, `add_textbox`, `add_multiline_textbox`, `add_box`, `add_icon`, `add_footer_logos`, `two_card_slide`, `content_with_items`, `icon_content_slide`, `_nuke_effects_from_xml`, `remove_shadow`.

**Known constraints:**
- Cybfont as a true font is not installed locally → use PNG icons from `icons_png/` as substitute.
- Templates with >2 slides cause orphaned ZIP entries when slides are removed from `sldIdLst` — always start from a clean 2-slide template.
- Output should be tested in Google Slides for each new slide type.

**Tested deliverables:** "VDI & VDA Para Instituciones Educativas" v1 (442 shapes, `build_final_pptx.py`); "CISO Risk Lens: Thinfinity vs Citrix" v2 (`build_ciso_pptx.py`). Slide count for each is dictated by the source PPTX, not by the pipeline.

## SVG Blog Illustration Pipeline

> **Note (2026-06):** this pipeline and the *Blog Cover Generation System* below are **two instances of the same task** — generating on-brand visuals for a Cybele blog article. ### Purpose

Generate branded illustrations for Cybele blog articles as **editable SVGs** that can be opened, adjusted, and finalized in Figma. ### Visual style rules

**Reference:** Figma `1rA3ZWuHPxh1BW2YXfF1LR` (Blog Posts — 2026). Authoritative tokens (typography, accent colors, layouts) live in the Figma file; only summary kept here.

- Canvas: 1920×1080. Content fills ~70%.
- Mode mix: alternate dark/light across the set (e.g., L/D/L for 3 illustrations) — never uniform.
- Backgrounds: linear gradients (dark `#0b1120 → #0e1726`; light `#f8f5fc → #f0ecf6`).
- Titles ~52px Inter 700; subtitles ~26-28px; body 18-20px.
- Layouts in use: hub-and-spoke, numbered cards in zigzag, center logo + 4 features.
- Title max 6 words; descriptions 1–2 sentences (what + why).

### Cybfont iconography

**Source:** Figma `x0HMD1pXkcYdFM7NSaBvb4` (Cybele Design System) → node `8120:7263`. Variants per icon: `light`, `bold`, `filled-bold`.

**Process to embed a Cybfont icon as native SVG:**

1. Match the icon by concept (`shield-ok` for backup, `import-export` for VM migration, etc.).
2. Get the variant's symbol node ID from the Design System file.
3. Call `get_design_context(nodeId, fileKey, excludeScreenshot=true)` → returns an asset URL.
4. **Key discovery:** that URL (`figma.com/api/mcp/asset/UUID`) returns **native SVG**, not PNG. Fetch the SVG text, extract `viewBox` + inner `<path>`/`<g>` elements.
5. Embed wrapped in `<g transform="translate(x,y)"><svg ... viewBox="...">`. Colorize via regex on `fill`/`stroke` before embedding.

### SVG-export pipelines

**Python (preferred, simpler):** `~/Downloads/build_blog_svgs.py` reads local SVG icons from `cybele_deckgen/icons/`, recolors via regex, builds illustrations programmatically, writes to `~/Downloads/`.

**Node.js (original, when Cybfont icons not available locally):** `~/dashboard/export-native-svgs.mjs` uses Puppeteer to fetch icon asset URLs from the Figma API, parses returned SVG text, builds and writes SVG files.

**Figma-compatible SVG rules:** only native primitives (`<rect>`, `<circle>`, `<text>`, `<path>`, `<line>`, `<polygon>`, `<linearGradient>`, `<g>`, nested `<svg>`). `<foreignObject>`, base64 `<image>`, and external URL references are silently dropped on Figma import.

## Blog Cover Generation System

> **Note (2026-06):** unified with the *SVG Blog Illustration Pipeline* above under the Claude Skill `cybele-blog-visuals`. The skill produces both covers (6 variants) and section illustrations in a single invocation. Section kept here because the output (hero image) is visually distinct from in-article illustrations, but operationally it's part of the same skill flow.

### Purpose

Generate branded **hero images for blog articles** (the cover image displayed at the top of each blog post). Distinct from the in-article illustrations only in placement and intent — covers express the **core concept of the article** as a single visual piece.

### Input / Output

| Input | Output |
|-------|--------|
| Article text (full copy or summary) | 6 cover variants, 1920×1080 SVG each |
| Core concept (one-sentence distillation) | HTML preview with all 6 stacked vertically for comparison |
| (Optional) Target Figma fileKey + nodeId | After approval: one native Figma-safe SVG |

### Workflow (canonical, every invocation)

1. Read the article; distill the core concept into one sentence
2. Pick 6 kits `{archetype, gradient_recipe, hero, satellites}` varying all four
3. Generate 6 SVGs at 1920×1080
4. Build a single HTML preview with all 6 stacked vertically, each labeled
5. Show preview in browser; wait for user to pick one (or request tweaks)
6. Export the chosen SVG as native Figma-safe output

**Rule:** the 6 variants are **6 ways to draw the same core concept**, NOT 6 different angles on the article.

### Visual system (overview)

The full spec lives in `cybele_deckgen/blog_covers/BLOG_COVER_RULES.md` (reverse-engineered from 21 reference covers in `sample portadas.pdf`). Summary:

- **Canvas:** 1920×1080 (16:9), min 60 px edge padding.
- **Design tokens (named):** `blue-deep`, `blue-royal`, `cyan`, `teal`, `violet`, `violet-light`, `magenta`, `warning`, `danger`, `danger-deep`, `ink`, `paper`, `white`. Each maps to a specific role (text/surface/accent/semantic).
- **Gradient recipes:** `cyan-to-blue` (default positive), `violet-to-blue` (product-hero), `teal-to-navy` (compliance/reliability), `red-dramatic` radial (problem covers only), `monitor-body` (device frames), `halo` (always behind the focal element).
- **6 compositional archetypes (A1–A6):** Hub-and-spokes / Duality / Hero+halo / Stack-ecosystem / UI mockup (2 flavors: agent console vs admin dashboard) / Editorial-poster (2 flavors: dark for "problem" covers, poster for aspirational hero).
- **Hero primitive library (13):** shield, cloud, padlock, monitor/desktop, laptop, server rack, factory silhouette, robotic arm, graduation cap, gears, coins, agent with headset, Thinfinity ring. Compound heroes (e.g. cloud+padlock) are common.
- **Satellite vocabulary:** circle badges (60–100 px, color-coded by semantic), connection lines (4–6 px white), halos, rings, label pills (navy bg + Inter SemiBold), logo chips.
- **Editorial rules (mandatory):** the 6 variants are 6 ways to draw **the same core concept** (never 6 angles); don't default to red for "big" (red-dramatic = pain only); titles in chips, not floating text; one focal per cover; products over third-party logos.
- **Topic → kit lookup table** in `BLOG_COVER_RULES.md` covers the common Cybele article topics (Security / Cloud migration / OT-IT / VDI / Contact center / Cost-ROI / Pain point / Automation / Monitoring / Transformation / Product hero).

### SVG authoring (Figma compatibility)

Same strict rules as Blog Illustrations — native primitives only:

- **Allowed:** `<rect>`, `<circle>`, `<ellipse>`, `<path>`, `<line>`, `<polygon>`, `<polyline>`, `<g>`, `<svg>`, `<linearGradient>`, `<radialGradient>`, `<defs>`, `<filter>`, `<text>`, `<tspan>`.
- **Forbidden:** `<foreignObject>`, `<image>`, external `<use>`, base64 data URIs, external URL references.
- Escape `&` → `&amp;` in `<text>`. Prefix SVG IDs per cover (`c1-bg`, `c2-halo`) to avoid silent fill breakage. Use `gradientUnits="userSpaceOnUse"`. No CSS classes / `<style>` blocks.

Python-only generator. Builds SVG programmatically (parameterized by archetype × tokens × hero × satellites), writes file, renders PNG via Playwright, emits `preview.html` with the 6 variants stacked vertically for review. Templates were dropped during reconciliation — the batch-generate → review → export workflow makes generator + helpers the simpler win on consistency and propagation of brand changes.

## Thinfinity Architecture Diagram Skill

### Purpose

Generate **Thinfinity (Cybele Software) product architecture diagrams** as native, Figma-compatible
SVG, built from a small, strict visual vocabulary reverse-engineered from Cybele's official Figma.
Distinct from the Blog pipelines: this is not editorial illustration — it is **technical diagramming
from fixed atoms on a grid**. Output is a standalone SVG + an HTML preview, optionally pushed to Figma.

The skill is **packaged and live** at `~/.claude/skills/thinfinity-architecture/` and auto-invokes
whenever the user asks to create/draw/diagram a Thinfinity or Cybele architecture (deployment topology,
reference architecture, gateway/broker/IDP layout, VDI/DaaS topology, multi-region/multi-tenant setup,
or to redraw an existing architecture image in the Cybele style).

### Input / Output

| Input | Output |
|-------|--------|
| Natural-language description of an architecture (explicit OR conceptual — see modes below) | Standalone SVG (icons inlined) |
| (Optional) an existing architecture image to redraw in the Cybele style | HTML preview (`test_NN.html`) for browser inspection |
| (Optional) target Figma `fileKey` + `nodeId` | After approval: native Figma-safe push via `generate_figma_design` |

### Visual System (the "pill" vocabulary)

Reverse-engineered from Figma files `8RBfhSYgaCuo4uM82JqAHL` (canonical atoms — 5 reference frames
Nick curated) and `W3Pnm739iwmVdo3hSaBNQe` (131-icon library). Authoritative spec: `SKILL.md`
(inside the skill) + `STYLE_SPEC.md` (in the working dir).

- **The pill (one atom for everything):** uniform **160×43 px**, 1.5 px solid border, radius 7, white
  fill always, icon 23×23 at (10,10), Inter 12 px label. **No size variants.** Category is communicated
  **only by stroke + text color**:
  - **Thinfinity** = Cybele blue `#0A74D6` (Gateway, Broker, IDP, Agent, Comm Gateway)
  - **User** = dark `#373737` (browsers, end users)
  - **Secondary** = gray `#BDBDBD` stroke + `#373737` text (resources, firewall, TLS tunnel, DB)
  - The icon keeps its native brand color — only the box stroke + label carry the category color.
- **Zones = dashed containers** (`stroke-dasharray="6 4"`) labeling a network/site/tier: Remote Access,
  DMZ, Corporate/Internal Network, Cloud, On-Prem, IDP Integration, region bands. **Hard rule: no dashed
  inside dashed** — subnets/pools/domains become pill rows with a text label, not sub-boxes.
- **Connector = open chevron stroke** in azure `#0AA9FF` (NOT the Cybele `#0A74D6`, NOT a filled
  triangle), width 2, orthogonal routing, buses for converge/distribute. **Dashed connector** = a
  secondary/support flow (IDP auth, management, backup).
- **Layer order (hard rule):** zones → connectors → pills, or arrowheads get hidden.
- **Default is monochrome**; per-flow color-coding is an opt-in exception (e.g. color per region in
  multi-region diagrams).
- **131 brand icons** in `icons/` (+ `_arrow.svg`), native viewBox 23×23, fixed `preserveAspectRatio`
  (`xMidYMid meet`) so they don't deform.

### Product knowledge layer (capability → topology)

A second layer was specified so the skill can produce a diagram from a **conceptual description of
Thinfinity capabilities**, not only from an explicit list of boxes and arrows. Captured in
`thinfinity_arch_skill_handoff_v2.md` (Downloads). It adds:

- **Component catalog** (role → pill): Gateway, Primary/Secondary Broker, IDP, Agent, Comm Gateway,
  endpoints, backend resources, TLS tunnels, external IDPs.
- **Zone catalog** and **product invariants** (the non-negotiable rules the skill applies even when
  unspoken): reverse connection / no inbound ports (arrows point to the Gateway); Gateway lives in the
  DMZ/Cloud; Broker lives in the corporate network with the resources; clientless browser access; HA =
  Primary + Secondary Broker; TLS 1.3/443 transport; multi-region = per-region Comm Gateway + Sec Broker;
  multi-domain = per-domain Primary Broker; IDP auth drawn dashed; managed/DaaS = "Managed by Cybele
  Software" hub-and-spoke.
- **Capability → topology map**: translates "clientless access", "no open ports", "VDI/DaaS", "SSO/MFA",
  "multi-region", "hybrid", etc. into the concrete components to instantiate.
- **Two prompt modes** converging on the same render pipeline:
  1. **Explicit** — user enumerates zones/nodes/flows (validated, in production).
  2. **Conceptual** — user describes capabilities; the skill derives the topology via the invariants.
